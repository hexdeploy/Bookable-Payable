## 1. What did you eventually understand about these documents that you did not understand on day one?

On day one I assumed every PDF in the set would be an invoice or credit memo — something clearly payable. That assumption broke immediately. DU-03 turned out to be a multi-document PDF bundling an invoice together with a shipment cartage advice, a customs permit, and a house air waybill — four distinct documents in one file. DU-05s was a delivery note paired with a shipment receipt. DU-08 was a German payment reminder (Mahnung) listing past transactions. DU-09 was an internal donation and sponsorship approval form — not a supplier document at all. None of these are payables, but they all arrive in the same folder with the same file extension. The classification step turned out to be as important as the extraction step.

The second thing I got wrong early was the meaning of `unit_price`. I initially extracted it as whatever number appeared next to the line description on the document — which on some documents is the gross (tax-inclusive) price. The ERP computes `gross = sum(qty × unit_price) + taxes`. If `unit_price` already includes tax and the tax is also listed separately in `taxes[]`, the ERP double-counts it. DU-06, DU-10, and DU-11 all failed this way on first pass — ERP computed more than the document stated because both the gross unit price and the separate tax amount were submitted. The fix was to back-calculate the net: `net = gross_price / (1 + rate/100)`. This is not obvious from the document surface because the document shows the gross price as the "price" — you have to reason about what the ERP will do with that number.

Tax placement was a third surprise. The grading separates getting the right gross total from getting the right structure. A header-level tax applied at the wrong level (moved to each line, or vice versa) changes the base the ERP uses to recompute it. INV-01 had a 0% reverse-charge VAT — a German supplier billing an Estonian company where VAT is not charged by the supplier. That still needed a tax entry with rate 0% and amount 0.00 in `taxes[]`, because the ERP expects the tax record even when the amount is zero.

## 2. When your system meets a document unlike any it has seen, what does it actually do — and why does that generalise instead of guessing?

The system does not contain any document-specific rules. There is no code that says "if the filename starts with INV, do X" or "if the supplier is from Germany, apply 19% VAT." Every document goes through the same three steps: extract text (pdfplumber for text-layer PDFs, PyMuPDF + Tesseract OCR for scanned ones), send that text to Gemini with a principle-based prompt, then fuzzy-match the output against master data. The prompt instructs the model on *how to reason* — unit_price is always NET, taxes go where the document puts them, unknown fields stay blank — not on what specific values to expect.

When the system meets a new tax type it has not seen before, the prompt rule "copy the tax name and rate exactly as printed, leave tax_type_code blank" applies. The resolver attempts a fuzzy match against `tax_master.json` by rate and country; if it finds no match it returns an empty string. An honest blank is submitted. The ERP still computes the correct gross if the rate and amount are right, even if the code field is empty. Similarly, a new supplier not in `suppliers.json` gets an empty `supplier_id` — the rest of the payable (amounts, dates, line items) is still correct and still books. The system does not fabricate a supplier ID to appear more complete.

This matters for the held-back document set because any document-specific shortcut that works on the open set will fail on a new layout. The principle "unit_price is always net" applies to every invoice regardless of country, currency, or layout. The principle "decline anything that is not an INVOICE or CREDIT_MEMO" applies to every non-payable regardless of what it looks like. These rules do not need to be retrained for a new document — they are already in the prompt.

## 3. Was there a document you concluded could not be solved the way the others were?

DU-02 is the document where the extraction approach breaks down. It is a large multi-page PDF — the OCR extraction produced 16,743 characters of text, the largest in the set. On every attempt, Gemini hit its output token limit mid-response and returned a truncated, unparseable JSON. The document appears to contain a complex multi-page invoice with many line items, but the combination of OCR noise from scanned pages and the sheer volume of content means the full line-item table cannot be transmitted to the model and extracted in a single pass within normal token limits. Increasing `max_output_tokens` to 16,384 and trimming the input to 10,000 characters was the mitigation, but this means later pages of the document are silently dropped from the extraction — any line items appearing after the 10,000-character cut are not captured.

The honest conclusion is that DU-02 requires a chunked extraction approach — split the document into page-level chunks, extract line items per chunk, then merge — which is a different architecture from what the rest of the documents need. For this submission, DU-02 is processed with best-effort extraction on the first 10,000 characters. If the gross does not match after merging partial line items, the payable is still submitted with what was extracted rather than declined, because the document is clearly an invoice and the partial data is better than nothing.
